# ResProbe

> Windows 显示器分辨率变化探测、远程桌面诊断与虚拟显示器兜底工具
> 版本 `1.0.0` ｜ 平台 Windows 10 / 11 **x64** ｜ **需要管理员权限**

一句话说明：当"**物理关闭显示器后桌面掉到 1024×768**"发生时，ResProbe 能证明责任在**主机显示链路**
（HDMI/DP 的 HPD 断开 → EDID 丢失 → 系统回退默认模式）而不是远程控制软件，并借助虚拟显示器把
桌面稳定在参考分辨率（默认 `1920x1080`），使远程会话不再随物理显示器一起"掉档"。

- 面向使用者：见 §1 – §9。
- 面向贡献者：见 §10 贡献指南 与 [DEVELOPMENT.md](DEVELOPMENT.md)（内部实现、接口契约、数据模型）。

## 1. 项目要解决的问题

**现象**：被控电脑物理关闭显示器后，桌面分辨率从 1920×1080 掉到 1024×768；此时用 ToDesk /
向日葵 / RustDesk 远程查看，看到的也是 1024×768；显示器重新上电后分辨率自动恢复。

**实测确认的根因链**（本机复现，2026-10-08）：

```
按显示器电源键
  → HDMI HPD 拉低，链路断开
  → 主机读不到 EDID（DISPLAY1/2/3 的 EDID 全部消失）
  → 监视器设备节点消失、驱动首选模式降级 1920x1080 → 1024x768
  → 模式表从 298 项退化为 32 项「通用回退列表」
  → 系统回退到默认模式 1024x768
  → 远程软件只是被动跟随主机帧缓冲，不是诱因
```

**三个曾经误导排查的错误方向**（都已排除，别再重复）：

| 被怀疑项 | 实测结论 |
|---|---|
| 系统省电关屏（`SC_MONITORPOWER`） | **不会**断链：EDID 仍可读，分辨率保持 1920×1080 |
| 显示器电源通知（`GUID_CONSOLE_DISPLAY_STATE`） | 物理关屏时**一次都不触发**，只有拓扑推断能捕获到状态变化 |
| 软件强行回写分辨率 | 链路断开期间 `CDS_TEST` 预检通过，但三种 DEVMODE 变体实际应用**全部** `DISP_CHANGE_FAILED`（硬件限制，软件绕不过）|

## 2. 主要功能

工具分两层，**诊断层只读，兜底层才改系统状态**。

**诊断层**

| 能力 | 说明 |
|---|---|
| 显示拓扑探测 | 基于 `QueryDisplayConfig(QDC_ALL_PATHS)` 枚举全部输出路径（含未激活的虚拟/占位路径），采集适配器、GDI 设备名、当前/首选模式、桌面矩形、模式表 |
| EDID 读取与关联 | 走 SetupAPI 读注册表 EDID，按**规范化设备实例 ID 精确匹配**（不无条件用厂商+产品码兜底，否则"显示器断电"会被同型号显示器顶替而掩盖故障）|
| 事件监听 | 顶层隐藏窗口监听 `WM_DISPLAYCHANGE` / `WM_DEVICECHANGE` / `WM_SETTINGCHANGE` / `WM_POWERBROADCAST` / `WM_WTSSESSION_CHANGE`，事件带合并窗口与上限，保证不漏掉抖动过程 |
| 会话与远程软件识别 | `WTS*` 会话信息（协议、客户端地址、连接状态）+ 五面扫描远程/虚拟显示痕迹（显示适配器、监视器设备、SetupAPI 设备、进程、服务）|
| 模式可用性验证 | 模式表查询 + `CDS_TEST` 只读预检（**预检通过 ≠ 实际可应用**，界面文案一律带此限定）|
| 时间线根因判定 | 基于**整条时间线的最差状态**（不是首尾对比）输出判定码、置信度、责任方、依据与建议；支持双端比对（`--peer`）|
| 结构化报告 | 显式 `--out` 才落盘；JSON 含拓扑、EDID（原始字节）、事件、判定与动作记录 |

**兜底层**

| 能力 | 说明 |
|---|---|
| 虚拟显示器 | 内置 usbmmidd v2 间接显示驱动（IDD），离线可用 |
| 幂等拓扑接口 | `ensure` 把拓扑调整到期望状态，退出码 `0/20/21` 即脚本判据 |
| 自动守卫 | `watch --guard`：检测到物理链路断开且虚拟屏可用时，自动把虚拟屏提升为参考分辨率主屏，并摘除断链死输出 |
| 图形入口 | 系统托盘图标 + 弹出菜单（**左键或右键**都能打开；含状态报告、分辨率调整、隐私屏、安装/卸载、自启开关、日志查看），与命令行共用同一批动作 |
| 动作层自检 | `selftest` 把托盘菜单依赖的全部函数跑一遍并逐项判定，托盘菜单无法自动点击，这是它唯一的脚本化回归入口 |

## 3. 系统要求与依赖

| 项 | 要求 |
|---|---|
| 操作系统 | **Windows 10 / 11 x64**（依赖 WDDM 显示配置 API 与 `IddCx` 间接显示框架；usbmmidd 官方自述为 Windows 10）|
| 权限 | 只读探测也**需要管理员**（清单为 `requireAdministrator`，见下方说明）；改拓扑、装驱动、注册计划任务必须管理员 |
| 语言标准 | C++17 |
| 编译器 | MinGW-w64 g++（本机验证 15.2.0，默认 `C:\mingw64\bin`）；代码同时兼容 MSVC 2019+ |
| 资源编译器 | `windres`（随 MinGW-w64 提供，编译图标 / manifest / 版本信息）|
| 构建工具 | `mingw32-make`（**无 CMake 依赖**，刻意保持"拷走源码 + 有 g++ 就能编译"）|
| 系统库 | `user32 gdi32 setupapi wtsapi32 powrprof advapi32 shell32 ole32 oleaut32`（全部系统自带）|
| 第三方运行时 | **无**（`-static-libgcc -static-libstdc++`，无 .NET / Python / VC++ 运行库依赖）|
| 内置驱动 | `driver/usbmmidd_v2/`（Amyuni usbmmidd v2，用户态 UMDF 驱动，已 WHQL 签名；许可见 §11）|

> **关于"只读命令也要管理员"**：清单里 `requestedExecutionLevel = requireAdministrator`。原因是
> 托盘菜单里几乎所有动作都需要管理员，脚本侧本来也用 `fltmc` 强制检查。代价是**从非提升的
> 控制台直接运行 `resprobe.exe` 会另起一个提升进程**：stdout 与退出码都会丢（这是预期行为）。
> 因此请始终在**已提升**的控制台里执行命令（`fltmc` 能成功即已提升）。

## 4. 安装

### 4.1 获取源码并编译

```bat
:: 在【已提升】的控制台中执行
cd /d <项目目录>
编译.bat                :: 等价于 mingw32-make；产物 resprobe.exe
编译.bat clean          :: 清空重建
```

>`编译.bat` 会把 MinGW 的 bin 目录注入 `PATH`（默认 `C:\mingw64\bin`）。装在别处时先
>`set MINGW_BIN=D:\mingw64\bin`。
>
>**注意**：仓库**不提交** `resprobe.exe`（见 `.gitignore`），克隆后必须自行编译，或直接运行
>`安装.cmd`（它会在缺少 exe 时现场编译）。

### 4.2 一键安装（推荐，幂等）

```bat
:: 在【已提升】的控制台中执行；可重复执行，每步都先查状态再动作
安装.cmd
```

`安装.cmd` 的 8 个步骤：

| 步骤 | 动作 | 幂等判据 |
|---|---|---|
| 1 | 确保 `resprobe.exe` | 已存在则跳过；缺失则调 `mingw32-make` 现场编译 |
| 2 | 确保 `OUT\` 输出目录 | `mkdir` 失败即已存在 |
| 3 | **定位驱动包**（三级回退） | ① 内置 `driver\usbmmidd_v2\` ② 迁移旧位置 `C:\Temp\...` ③ 联网下载 |
| 4 | **创建 ROOT 枚举的设备节点** | `pnputil /enum-devices /class Display` 出现 `USB Mobile Monitor` 则跳过 |
| 5 | 写虚拟显示器分辨率表 | `reg add /f` 覆盖写 |
| 6 | **激活恰好一块虚拟显示器** | 依赖 `resprobe ensure` 返回 `20`；已有虚拟屏则不再 `enableidd 1` |
| 7 | 应用显示拓扑 | `resprobe ensure` 内部先判"已就绪"再决定动作 |
| 8 | 汇总结果 | — |

> 第 4 步是全新机器上的关键：`pnputil /add-driver` 只把驱动包放进 DriverStore，
> **不会创建设备节点**；必须用驱动包自带的
> `deviceinstaller64.exe install usbmmIdd.inf usbmmIdd`。缺了它，第 6 步的 `enableidd 1`
> 会**静默失效**（设备在跑，但一个虚拟显示器都没有）。

### 4.3 注册开机自启（可选）

```bat
开机自启.cmd                    :: 默认注册「虚拟屏初始化 + 常驻守卫」两个登录任务
开机自启.cmd /mode once         :: 只注册初始化，不注册守卫
开机自启.cmd /status            :: 查看注册状态
开机自启.cmd /remove            :: 注销全部
```

注册的两个任务均为「登录触发 + 最高权限」：

| 任务名 | 目标脚本 | 延迟 | 为什么需要 |
|---|---|---|---|
| `ResProbe VDisplay Init` | `一次性启动.cmd` | 20 秒 | usbmmidd 虚拟屏**不跨重启保留**，必须先重新激活 |
| `ResProbe Guard` | `常驻守卫.cmd` | 60 秒 | 常驻守卫，需等虚拟屏就绪后再启动 |

### 4.4 卸载

```bat
卸载.cmd                :: 注销任务 + 停守卫 + 移除虚拟屏（保留驱动，可重装）
卸载.cmd /full          :: 连驱动一起移除
卸载.cmd /purge         :: 再删除 OUT 目录与内置驱动包
```

## 5. 运行与使用示例

### 5.1 最小可用示例

```bat
:: ① 关显示器之前：先留一份基线（只读）
resprobe.exe snapshot

:: ② 开着监听，物理按显示器电源键关屏，等 10 秒再开回来
resprobe.exe watch --duration 120 --interval 10 --guard

:: ③ 显示器保持关闭，再看一次当前状态
resprobe.exe snapshot
```

**判定标准**

| 观测项 | 已修复（有虚拟屏兜底） | 未修复（故障态） |
|---|---|---|
| 主屏 | `1920x1080 @ (0,0)` | `1024x768` |
| 活动输出数 | **1**（仅虚拟屏） | 2 ~ 3（含断链死输出） |
| 桌面尺寸 | 恰为 `1920x1080` | `2048x768` / `3968x1080` 等 |
| `edid.present` | 虚拟屏 `false`，物理屏已从桌面移除 | 死输出仍 `ACTIVE` |

### 5.2 常用命令

| 目的 | 命令 |
|---|---|
| 一次性体检 | `resprobe.exe snapshot` |
| 列出全部输出路径（含占位路径） | `resprobe.exe paths --verbose` |
| 回写前只读验证 + 双端比对 | `resprobe.exe verify --peer samples\peer-degraded-1024x768.json` |
| 幂等把拓扑调到期望状态（脚本用） | `resprobe.exe ensure`（`--mode auto\|mirror\|promote`）|
| 无显示器 / 显示器不再接回 | `一次性启动.cmd` |
| 常驻守卫（默认开机启动方式） | `常驻守卫.cmd /bg`（`/json` 额外写状态 JSON）|
| 图形界面（托盘） | 双击 `resprobe.exe` 或 `resprobe.exe tray` |
| 手动改拓扑（**会改系统状态**） | `resprobe.exe vdisplay --yes --mirror` / `--yes --promote` |
| 手动回写分辨率（**会改系统状态**） | `resprobe.exe restore --reference 1920x1080 --yes` |
| 托盘动作层自检 | `resprobe.exe selftest` |
| 写证据报告 | 任意子命令加 `--out report.json`（默认**不落盘**）|

### 5.3 命令行选项

| 选项 | 适用 | 默认 | 作用 |
|---|---|---|---|
| `--reference WxH` | 全部 | `1920x1080` | 参考健康分辨率；判定、验证、提升都以它为准 |
| `--out FILE` | 全部 | 不写 JSON | 显式指定才落盘；纯文件名落到输出目录，并派生同名 `.peer.json` |
| `--out-dir DIR` | 全部 | `<程序目录>\OUT` | 覆盖输出目录 |
| `--no-cds-test` | 全部 | 关闭（即默认执行） | 跳过 `CDS_TEST` 只读探测 |
| `--no-event-log` | `watch` / `tray` | 关闭（即默认写） | 不写精简事件日志 `OUT\events.log`（见 §5.5）|
| `--verbose` / `-v` | 全部 | 否 | 更详细的输出；`paths` 下会列出全部占位路径 |
| `--quiet` / `-q` | — | — | ⚠️ 当前**无效果**（保留参数，见 §12） |
| `--peer FILE` | `verify` / `watch` | — | 对端 `*.peer.json`，启用双端比对 |
| `--mode auto\|mirror\|promote` | `ensure` | `auto` | `auto` = 有健康物理屏则镜像、否则提升虚拟屏 |
| `--duration SEC` | `watch` | `0`（直到 Ctrl+C） | 监听时长上限 |
| `--interval SEC` | `watch` | `30` | 心跳采样间隔，`0` 关闭 |
| `--settle MS` | `watch` | `800` | 事件后等待驱动稳定的毫秒数（合并窗口上限为其 3 倍）|
| `--guard` | `watch` | 否 | 启用自动守卫 |
| `--no-guard` | `tray` | 否 | 托盘只提供界面，不做任何拓扑动作（**默认是开守卫的**）|
| `--yes` / `-y` | `vdisplay` / `restore` | 否 | **必需**，确认执行系统状态变更 |
| `--mirror` | `vdisplay` | 否 | 复制（镜像）拓扑 |
| `--promote` | `vdisplay` | 否 | 提升虚拟屏为主屏 + 摘除断链死输出 |

> 未知参数只会**警告并忽略**（不报错退出）——保证新旧版本脚本可以互相调用而不互相打断。

### 5.4 退出码

| 退出码 | 出现位置 | 含义 |
|---|---|---|
| `0` | 全部 | 成功（`ensure` 特指"**兜底能力已就位**"）|
| `1` | 诊断类子命令 | 参数或执行失败；**含"给了 `--out` 但报告写不进去"** |
| `3` | `watch` / `tray` | 无法创建监听窗口 |
| `4` | `tray` | 托盘图标创建失败（常见：`explorer.exe` 未运行）|
| `5` | `tray` | 已有托盘在运行 |
| `20` | `ensure` | 没有可用的虚拟显示输出 → 先 `deviceinstaller64.exe enableidd 1` |
| `21` | `ensure` | 已调整，但主屏仍未达到参考分辨率 |
| `N` | `selftest` | **失败项数量**（`0` = 全部通过）|

### 5.5 精简事件日志（`OUT\events.log`）

监听类子命令（`watch` / `tray`，含 `常驻守卫.cmd`）默认会额外维护一份**只记变动**的日志：
`<程序目录>\OUT\events.log`。一次实际变化一行，追加写，不轮转。

```
2026-10-19 10:27:32 #1 [启动] 基线: 主输出 1920x1080 (\\.\DISPLAY1), 活动 2/连接 7, 电源 ON(推断 ON)
2026-10-19 10:36:25 #2 [设备移除+显示变化 1920x1080+设备到达] 电源(推断) ON->OFF | 主输出 \\.\DISPLAY1 -> \\.\DISPLAY14 | 物理屏离线 VA2702-H x3
2026-10-19 10:36:40 #3 [设备移除+显示变化 1920x1080+设备到达] 电源(推断) OFF->ON | 主输出 \\.\DISPLAY14 -> \\.\DISPLAY1 | 物理屏在线 VA2702-H x3
2026-10-19 14:02:33 [守卫] #3 接管: 主输出 1920x1080 (\\.\DISPLAY5)
```

格式为 `<本地时间> #<序号> [<触发原因>] <变化1> | <变化2> | ...`。

内容**不是逐字段罗列差分，而是聚合后的摘要**。上面第 2、3 行对应"关闭物理显示器 /
重新打开"：原始差分有 11 条、约 700 字符（`\\.\DISPLAY1: 8bpp -> UNKNOWN`、
`模式数量 298 -> 0`，且 `\\.\DISPLAY2` / `\\.\DISPLAY3` 是同一台屏的克隆、各重复一遍），
摘要后是 3 条、约 120 字符。

可出现的条目：

| 条目 | 含义 |
|---|---|
| `电源(通知) A->B` / `电源(推断) A->B` | Windows 的显示输出状态 / 由 EDID 可见性推断的状态 |
| `主输出 \\.\DISPLAY1 -> \\.\DISPLAY14` | 主输出设备切换 |
| `分辨率 1024x768 -> 1920x1080` | 主输出分辨率变化 |
| `物理屏离线 VA2702-H x3` | 有监视器掉线（EDID 与设备节点都消失）；**同一台屏的多个克隆只记一次** |
| `物理屏在线 VA2702-H x3` | 监视器恢复在线 |
| `新输出 \\.\DISPLAY5=1920x1080` / `输出消失 \\.\DISPLAY5` | 输出出现 / 消失（已被"主输出"体现的不重复记）|
| `活动 2 -> 1` | 挂到桌面的输出数变化 |

其他约定：

- **只写发生了变化的事件**。心跳、未变化的重新采样、快照全文、路径列表、远程软件痕迹、判定过程一律不写。
- `[启动]` 首行是基线锚点 —— 不带它，后面每一行 `A -> B` 都没有参照。
- `[守卫] #n 接管: ...` 是守卫自动改拓扑的记录：它本身也是变动，且比后续快照差分更早落盘。
- `#序号` 自每次启动重新从 1 计，因此同一天里第几次起跑也能区分。
- 与详细日志分工：**详细日志（`tray.log` / `guard.log`）留现场，`events.log` 留结论**。实测同一轮监听约 511 B / 4 行 vs 6.8 KB / 77 行。逐字段的完整差分仍保留在 JSON 报告（`--out`）里，摘要不丢信息。
- 用 `--no-event-log` 关闭；托盘菜单「查看最近的日志」默认会打开它（取 `OUT` 下最新 `.log`）。

常用查询方式：

```powershell
# 今天发生的全部变动
Select-String -Path OUT\events.log -SimpleMatch "2026-10-19"

# 只看电源状态变化
Select-String -Path OUT\events.log -Pattern "电源\("

# 只看物理屏掉线 / 恢复
Select-String -Path OUT\events.log -Pattern "物理屏(离线|在线)"

# 只看守卫接管
Select-String -Path OUT\events.log -Pattern "\[守卫\]"

# 实时跟踪（PowerShell 5.1）
Get-Content OUT\events.log -Wait -Tail 20
```

### 5.6 托盘图标的六种状态

托盘图标与悬停提示反映"现在处于哪种工况"，优先级从高到低：

| 优先级 | 判据 | 图标 | 悬停提示后缀 |
|---|---|---|---|
| 0 | 隐私屏生效（用户经菜单发起，**且**显示输出确实已关闭） | 🟣 紫（屏幕区带横条） | ` · 隐私屏中` |
| 1 | 没有可用的虚拟显示输出（`virtualAvailable == 0`） | 🔴 红 | ` · 无兜底` |
| 2 | 没有健康的物理屏，但仍有输出在活动 | 🟡 黄 | ` · 兜底中` |
| 3 | Windows 关闭了显示输出（`GUID_CONSOLE_DISPLAY_STATE = Off`） | 🔵 蓝 | ` · 显示输出已关闭` |
| 4 | 仍有物理显示器在线 | 🟢 绿 | ` · 显示器在线` |
| 5 | 其余（含探测失败、无任何活动输出） | ⚪ 默认 | 无后缀 |

提示文本形如 `ResProbe 1920x1080 · 兜底中`。

**为什么红/黄要压过蓝**："OS 空闲关屏"是常态且无害，而"兜底中 / 无兜底"才是要看的。若蓝压过黄，一次空闲关屏就会把兜底状态盖掉。

**为什么隐私屏压过一切**：它是用户主动发起的、瞬时的，且最能解释"屏幕为什么黑"。"无兜底"只是潜在风险，完整状态报告里能查到。

**为什么第 6 态用形状而不是第 6 种颜色**：6 种色相在 16×16 的托盘位图里已超过可分辨极限（默认本身就是青→蓝渐变，与"蓝"本就偏近）。隐私屏因此额外画了一条横贯屏幕区的横条，形状在小尺寸下远比色相可靠。

**三个边界**：

- 🟣 要求"显示输出确实已关闭"。屏幕被本地输入唤醒后，图标立刻回到真实状态（🟢/🟡/🔴/🔵），只有菜单文案仍显示"关闭隐私屏"——避免出现"屏幕亮着却显示隐私屏中"的谎报。
- `primaryMode` 为空（这次探测什么都没采到，或当前没有任何活动输出）时一律退回默认图标 —— 否则会把一次瞬时枚举失败报成红色告警。
- 🟡 的判据是"没有健康的物理屏"（EDID 与监视器设备节点都读不到）**且**仍有输出在活动；虚拟屏天生没有 EDID，因此"虚拟屏兜底中"不会被误判成"显示器在线"。

状态变更会同时写入 `OUT\tray.log`：

```
[托盘] 图标 -> 绿(显示器在线)
[托盘] 提示 -> ResProbe 1920x1080 · 显示器在线
```

> 物理关显示器（按显示器电源键）**不会**让 Windows 发出 `GUID_CONSOLE_DISPLAY_STATE = Off`，因此那种情况下图标走的是 🟡（靠 EDID 推断），不是 🔵。🔵 只对应 OS 主动关屏（空闲超时、锁屏）。

### 5.7 隐私屏（本地黑屏且动不了，远程仍可见可操作）

托盘菜单「开启隐私屏 / 关闭隐私屏」，与具体远控软件无关。

```
[隐私屏] 已开启：遮罩 1920x1080，捕获排除已生效，本地键鼠已屏蔽
[托盘] 图标 -> 紫(隐私屏中)
[托盘] 提示 -> ResProbe 1920x1080 · 隐私屏中
```

**实现方式**：全屏置顶黑窗口 + `SetWindowDisplayAffinity(WDA_EXCLUDEFROMCAPTURE)` + 底层键鼠钩子。生效时本地看到黑屏、本地键鼠被吞掉，而捕获端（远控）看到的是正常桌面，能正常点击、正常打字。

**为什么不用"关闭显示输出"**（这是最初的方案，真机验证后废弃）：

- `rustdesk.exe` 持有 `DISPLAY` 电源请求（`powercfg /requests` 可见），会在关屏后不到 1 秒把显示输出要回去，且**没有 API 能释放别的进程的电源请求**；
- 就算关掉了，任何键鼠输入都会立刻点亮它 —— 而在底层钩子里吞掉物理输入**并不能**阻止这一点（实测吞掉 643 个物理事件后 `GetLastInputInfo` 仍被钉在 0~109ms，而无人操作时它每秒 +1000ms），说明输入在到达钩子之前就被电源管理器记下了。

**四个实现约束**（都是真机踩出来的，改代码前务必看 `src/privacy.h` 的注释）：

| 约束 | 不这么做会怎样 |
|---|---|
| 点击穿透用 `WS_EX_LAYERED \| WS_EX_TRANSPARENT` | 用 `WM_NCHITTEST` 返回 `HTTRANSPARENT` 只对同线程窗口生效 → 远控"光标能动、点击失效" |
| 必须 `WS_EX_NOACTIVATE` + `SWP_NOACTIVATE` | 黑窗口变前台后远控的键盘全被吃掉，应用收不到字符 |
| 周期置顶用 `HWND_TOP` | 对已置顶窗口再调 `HWND_TOPMOST` 是空操作，压不住同为置顶的任务栏/弹出菜单 |
| `Start()` 先隐藏建窗、校验捕获排除生效后再显示 | 否则可能出现"本地黑了、远控端也黑了"，比不开更糟 |

**已知限制**：

- **光标盖不住**：窗口是点击穿透的，光标在命中测试上落在下层窗口、由那个窗口决定可见性，改本线程的 `ShowCursor` 计数无效。本地看到的是"一块黑屏 + 一个光标"，不泄露内容。
- **弹出菜单会有 ≤100ms 闪现**：菜单/开始菜单是别的进程的置顶窗口，靠 100ms 周期重新置顶去压，压住的瞬间之前会闪一下。
- **`Ctrl+Alt+Del` 无法拦截**（走内核/CSRSS，不经钩子）；`UAC`、`Win+L` 的安全桌面同理。这也是本地用户被锁住时的唯一逃生通道。
- **需 Windows 10 2004 及以上**（`WDA_EXCLUDEFROMCAPTURE`）。不支持时 `Start()` 会直接放弃并弹窗说明，**屏幕与远控都不受影响**。
- 显示器仍然点亮，**不省电**（只是看不到内容）。
- 托盘进程退出时会自动撤除遮罩并恢复本地输入。

**连点解除（逃生路径）**

隐私屏生效后本地键鼠全被吞掉，如果此时远程连不进来（断网 / 远控服务挂了），
坐在机器前的人无法用鼠标键盘操作任何东西。为此提供一条纯鼠标的逃生路径：

> **10 秒内连点鼠标 20 下**（任意键，左/右/中/侧键都算）即可**解除**隐私屏。

```
[隐私屏] 连点解除触发（10 秒内 20 次鼠标按下）
```

**单向，只解除不开启。** 这是刻意的取舍：

- 若允许连点开启，鼠标钩子就必须**常驻**在系统里（关闭状态下也得数点击）。代价是一个全局鼠标钩子长期挂着，既多一份侵入，也更容易被安全软件当成可疑行为。
- 而且正常使用中"每秒 2 次、持续 10 秒"的点击并不罕见（快速点列表、玩游戏），会让屏幕**突然变黑**——误触代价远大于收益。

所以钩子仍只在遮罩期间安装（`Start()` 装、`Stop()` 卸），关闭状态下系统里没有任何 resprobe 的输入钩子。

其余实现要点：

- **本地点击与远控注入点击都算**。这与"吞输入"的方向相反，但目的不同：吞输入要放行注入事件好让远控能操作；计数器则两种来源都要认，否则纯远程场合（看不到托盘界面）无法把隐私屏关掉。
- 钩子回调里**只写数组 + `PostMessage`**，真正的开关在主线程做（钩子里不能创建/销毁窗口）。
- 计数用 20 格固定环形数组、零堆分配；触发后窗口清零，不会重复触发。
- ⚠ 钩子回调由托盘主线程的消息泵派发，超过 `LowLevelHooksTimeout`（约 300ms）未处理的事件会被系统**跳过**。所以托盘线程不能做长时间阻塞操作，否则连点会"丢点"。弹窗安全，因为 `MessageBox` 的模态循环本身在泵消息。

**开启 / 解除都会弹确认框**：

| 时机 | 弹窗可见性 |
|---|---|
| **开启成功** | 遮罩已经在位，提示框是普通非置顶窗口 → **本地看不到**（避免"本地有个点不掉的模态框"这种死结），**远端能正常看到并点掉** |
| **解除成功** | 遮罩已撤除 → **本地与远端都看得见** |

弹窗是模态的，但模态循环本身在泵消息，100ms 置顶定时器与连点计数都不受影响。

> `ensure` 的 `0 / 20 / 21` 是脚本做幂等判断的**对外契约**：`0` 的语义是"兜底能力就位"
> （要求虚拟屏存在），不是"桌面当前看着正常"。**不要改成"看着正常就返回 0"**，
> 否则 `安装.cmd` 第 6 步会漏掉激活虚拟屏。

| `main.cpp` | CLI 解析与各子命令编排 | 不实现具体动作 |

## 7. 工作原理（简版）

```
                        ┌──────────────────────── 诊断层（只读）────────────────────────┐
  DisplayConfig ────────▶ display.EnumerateDisplays ─┐
  SetupAPI/EDID ────────▶ edid.EnumerateMonitorEdid ─┼─▶ DisplaySnapshot ─┐
  WTS / 进程 / 服务 ────▶ session.DetectRemoteSoftware┘                   ├─▶ verdict.EvaluateVerdict ─▶ 判定 + 依据 + 建议
  窗口消息（事件）──────▶ watcher.TakeSample ────────────────────────────┘                              │
                        └──────────────────────────────────────────────────────────────────────────────┼──────────┐
                        ┌──────────────────────── 兜底层（改状态）────────────────────────┐             │          │
  托盘菜单 / 命令行 ────▶ actions / main ──▶ verify.PromoteVirtualDisplay / ApplyDisplayMode ─▶ 桌面恒为参考分辨率
                        └───────────────────────────────────────────────────────────────────┘
                                        全部落盘：report.WriteJsonReport → OUT\*.json，日志 → OUT\*.log
```

**三个关键判据**（理解它们就理解了本项目）

| 判据 | 定义 | 为什么重要 |
|---|---|---|
| **链路健康** `IsLinkHealthy` | `edid.present && monitorDeviceNodePresent` | 三处判定（输出性质 / 拓扑计数 / 守卫）共用它；只看 EDID 会在"EDID 可读但设备节点已消失"的中间态误判 |
| **输出性质** `OutputNature` | `Virtual` / `HealthyPhysical` / `DeadPhysical` / `Mixed` | **失败归因的唯一依据**。虚拟屏 EDID 天然为空，若"见到没有 EDID 就说链路断了"，会把"虚拟屏不支持某档位"误报成硬件断链 |
| **兜底就绪** `ensure == 0` | 虚拟屏存在 **且** 主屏达参考分辨率 **且** 桌面无断链死输出 | 只看"桌面当前正常"会漏掉"虚拟屏其实不存在"，物理屏一断电就又掉档 |

**复制（镜像）拓扑是最大的坑**：此时多个输出共用同一个 GDI 源名（`\\.\DISPLAY1`），
`gdiDeviceString` / `adapterDevicePath` 都会串成物理适配器的描述，**所有基于名字的识别都失效**。
所以本工具的判据一律避免"用 `gdiDeviceName` 唯一定位输出"。

## 10. 贡献指南

### 10.1 开工前

1. **先把环境跑通**：`编译.bat` → `resprobe.exe selftest`（退出码必须为 `0`）。
2. **读这两处再动代码**：
   - [DEVELOPMENT.md](DEVELOPMENT.md) 的 **§3 模块划分**、**§6 接口与函数约定**（含行为契约）、
     **§12 代码规范与协作约定**（含"改一处必须同步改哪里"的影响面速查）；
   - 本文档 §7 的三个关键判据 —— 绝大多数历史缺陷都出在"判据不统一"上。
3. **有守卫/托盘在跑时必须先停掉**，否则 `.exe` 被占用无法编译：
   ```bat
   taskkill /im resprobe.exe /f
   ```

### 10.2 分支策略

本项目使用轻量级 **trunk-based** 流程（单人/小团队维护，无发布分支）：

| 分支 | 用途 | 命名 | 生命周期 |
|---|---|---|---|
| `main` | **唯一长期分支**，必须始终可编译、`selftest` 通过 | — | 永久 |
| 功能分支 | 新功能 | `feat/<简短主题>`，如 `feat/multi-monitor-layout` | 合并即删 |
| 修复分支 | 缺陷修复 | `fix/<简短主题>`，如 `fix/restore-attribution` | 合并即删 |
| 文档分支 | 只改文档 | `docs/<简短主题>` | 合并即删 |
| 杂项分支 | 构建/脚本/依赖等 | `chore/<简短主题>` | 合并即删 |

约定：

- **不直接在 `main` 上提交**；`main` 只接受合入（合并前必须构建通过）。
- 分支主题用**小写英文 + 连字符**，不要用中文（跨平台工具链对中文分支名的支持不一致）。
- 一个分支只做一件事；顺手重构请拆成独立分支/提交。
- 合并方式优先 **squash merge**（保持 `main` 线性、每个提交对应一个可独立理解的变更）。

### 10.3 提交信息规范

采用 **Conventional Commits**（中文正文可以，但**类型与范围保持英文**）：

```
<type>(<scope>): <subject>

<body 可选：为什么这么改、现象与根因>

<footer 可选：引用 / 关闭的 issue，如 Refs: #12>
```

**type**（与 §10.2 的分支前缀一致）

| type | 用途 |
|---|---|
| `feat` | 新功能 |
| `fix` | 缺陷修复 |
| `docs` | 仅文档 |
| `refactor` | 不改行为的重构 |
| `perf` | 性能 |
| `build` | 构建系统 / Makefile / manifest / 资源 |
| `chore` | 脚本、杂项、忽略规则 |
| `test` | 测试与自检用例 |

**scope**（用模块名，见 §6）：`display` `edid` `verify` `verdict` `watcher` `session` `report` `actions` `tray` `main` `makefile` `scripts` `docs`。

**subject**：祈使句、不加句号、不超过 72 字符；说明"做了什么"而不是"改了个 bug"。

示例：

```
fix(verify): 回写失败按输出性质归因，不再见无 EDID 就断言断链

虚拟/间接显示输出的 EDID 天然为空，旧写法会把"虚拟屏不支持该档位"
误报成"显示链路已断开、硬件无法绕过"，把排查引向错误方向。

Refs: #7
```

```
docs(readme): 补充安装、使用示例、贡献指南与已知限制
```

**必须遵守的两条**：

- **不要**在提交信息里粘贴大段日志或二进制；证据文件放 `OUT\`（已忽略）或 issue 附件。
- 涉及行为变更的提交，请在 body 里写清**失败路径的语义**（本项目多个缺陷都藏在失败路径里）。

### 10.4 硬性代码约束

这些约束不是风格偏好，破坏它们会导致**运行时**（而不是编译时）故障：

| # | 约束 | 原因 |
|---|---|---|
| 1 | `common.h` 必须是每个翻译单元的**第一个**头文件 | 它定义 `WIN32_LEAN_AND_MEAN` / `_WIN32_WINNT`，晚包含会导致 `QueryDisplayConfig` 等原型缺失 |
| 2 | **所有改系统状态的调用只能出现在 `verify.cpp`** | 保证诊断子命令（`snapshot` / `paths` / `verify`）绝不误改系统 |
| 3 | `verdict.cpp` 保持**纯函数** | 不调用 Win32 状态修改 API、不做 I/O；便于推理与复用 |
| 4 | **不引入第三方依赖，也不引 CMake** | 当前设计目标是"拷走源码 + 有 g++ 就编译" |
| 5 | `.cmd` / `.bat` 的**文件名可以中文，内容必须纯 ASCII**（UTF-8 无 BOM）| `cmd.exe` 按 OEM 代码页按字节偏移重读批处理；多字节字符会让偏移错位，把注释后半截当命令执行。改完跑 `脚本编码修复.ps1` |
| 6 | `.ps1` 也保持纯 ASCII | Windows PowerShell 5.1 对无 BOM 的 `.ps1` 按 ANSI 读取，中文易碎 |
| 7 | 不得修改 `driver/usbmmidd_v2/usbmmidd.inf` | 改动会使驱动数字签名失效 |
| 8 | 修正 `-Wall -Wextra` 的全部告警 | 构建须**零告警**（`-Wno-unused-parameter` 是唯一豁免）|
| 9 | 涉及退出码的改动必须同步 6 个脚本的 CONFIG BLOCK + `DEVELOPMENT.md` §6.5 + `PrintUsage()` | `ensure` 的 `0/20/21` 是脚本契约 |
| 10 | 测试数据与证据不要入库 | `OUT\` 已在 `.gitignore` 中；`samples\` 只放**夹具**（不属证据）|

### 10.5 提交 / 拉取请求（PR）流程

```
① 同步 main                  git switch main && git pull
② 建分支                     git switch -c fix/restore-attribution
③ 改代码 + 构建              taskkill /im resprobe.exe /f  →  编译.bat
④ 跑回归                     resprobe.exe selftest   （期望退出码 0）
                             DEVELOPMENT.md §7.6 本地回归清单（改到相关路径时全跑）
⑤ 自审 diff                  git diff --stat / git diff
⑥ 提交                       见 §10.3 的提交信息规范
⑦ 推送并开 PR                git push -u origin <分支>
⑧ PR 内容至少包含：
     - 问题与根因（现象、触发条件）
     - 改了什么（按模块列）
     - 怎么验证的（命令 + 实测结果；失败路径请给反向用例）
     - 影响面（是否触及 §10.4 的任何一条硬约束）
     - 是否需要同步文档（DEVELOPMENT.md 的哪些小节）
⑨ 评审要点（reviewer 必查）
     - 是否破坏了 §10.4 的 1~3、9（结构性约束与契约）
     - 判据是否统一到 IsLinkHealthy / OutputNature，有没有"第三份判据"
     - 失败路径的语义（退出码、消息、日志）是否与既有约定一致
     - 文档是否同步（尤其 DEVELOPMENT.md §6 接口契约、§9.7 已知限制、§14 版本更新记录）
⑩ squash merge 到 main，删除分支
```

**PR 检查清单（可直接粘贴到 PR 描述里）**

## 12. 已知问题与限制

完整清单（含编号 L-1 ~ L-13、影响与建议）见 [DEVELOPMENT.md](DEVELOPMENT.md) **§9.7**。
以下是使用者最可能踩到的部分：

**功能边界（暂不支持）**

| 限制 | 说明 |
|---|---|
| 多物理显示器 | 当前假设"单物理屏 + 虚拟屏"。多物理屏时目标屏挑选策略需要重新设计 |
| 服务化常驻 | 目前是"登录任务 + 前台进程"。Windows 服务会话无法操作桌面显示配置，改服务化须仍运行在交互式会话 |

**已知缺陷（不影响主流程，但请知悉）**

| 现象 | 影响 | 状态 |
|---|---|---|
| `--quiet` / `-q` 被接受但**无任何效果** | 期望"安静输出"的用户会失望 | 未修复（保留参数位）|
| 托盘的「关于」对话框列出一个**不存在的子命令** `record`，且漏了 `vdisplay` / `selftest` | 文案误导 | 未修复 |
| `--out` 出现在参数末尾（缺值）时提示为 `忽略未知参数 --out` | 提示措辞不准确（行为安全：等于不落盘）| 未修复 |
| `OUT\guard.log` 是 **UTF-8 + GBK 混合**编码，而 `常驻守卫.cmd` 头部注释仍称其为 UTF-8 | 用 `Get-Content -Encoding UTF8` 看会有一半乱码 | 注释待更正；读取请用托盘「查看最近的日志」|
| 有守卫在跑时再次运行 `常驻守卫.cmd`，会打印约 5 行 `The process cannot access the file … being used by another process` | **不是故障**：守卫独占持有 `guard.log` 的写句柄，脚本的日志追加被拒 | 已知现象 |
